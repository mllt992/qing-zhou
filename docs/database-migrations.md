# 数据库版本迁移

轻舟在接受 HTTP 请求、启动后台任务之前执行 `Store.Migrate()`。迁移失败会中止启动，日志保留具体版本 ID、失败阶段及原始 SQLite/IO 错误，不能将未知错误当作“已经执行过”。

## 版本和原子性

- `internal/store/migration_runner.go` 是追加式迁移注册表，ID 必须为正数、唯一且严格递增
- `schema_migrations.version` 使用 `000001_legacy_baseline` 这样的稳定名称，`applied_at` 为提交时的 Unix 秒时间戳
- 每个版本在独立的 `BEGIN IMMEDIATE` 事务里执行。建表、补列、回填、唯一约束/索引和版本标记一起提交或一起回滚
- 并发启动的迁移器先获取写锁，然后在同一事务内检查版本；已成功的版本不重复执行
- 遇到当前程序不认识的版本标记会拒绝启动，避免较旧程序误读新结构。使用相容版本，或按[灾难恢复指南](disaster-recovery.md)恢复配套快照；不要手工删除版本标记绕过检查
- 运行期清理过期凭据别名是独立维护操作，不是再次执行历史迁移，也不会延长别名有效期

## 已有数据库接入

第一版 `000001_legacy_baseline` 是截至引入版本体系时所有历史 DDL/回填/索引的**冻结基线**。将整段历史作为一个原子版本，避免按阶段提交后留下新结构和旧数据混合的中间态。空库和已有库经过相同入口。

兼容性通过 SQLite 表/列目录检查判断，不匹配错误字符串。已存在的邮箱豁免、sudo 列仍遵守历史的一次性分类条件；历史 zero-config、稳定凭据和有限流量标记保留，不重新授予访问或延长凭据宽限期。已完成稳定凭据迁移后，已撤销所有桶的账户不会因旧账户字段仍在而恢复权限。

旧版可能只完成部分非原子迁移。尚未完成桶模型切换的数据库会按账户恢复未完成的回填，已存在的桶不重复创建；广播父表/子表部分完成的结构也会补齐。对于无法区分“历史中断”和“后来由管理员明确修改”的安全敏感字段，不猜测并重新授权。

TLS 证书和探针 token 的历史回填必须使用正确的加密密钥。启动时先应用 `QZ_SECRET_KEY`；没有该环境变量的旧安装沿用数据库原有 `jwt_secret`。无法解密需要迁移的内容会使整个版本回滚，而不会把密文错误地作为 token 哈希或把证书迁移标记成成功。

异常数据违反唯一约束时，升级会明确失败并完整回滚。请保留数据库及升级前快照，在副本上定位重复项、确认业务归属后修复；不要通过删索引、删标记或忽略错误来强行启动。

## 添加以后版本

1. 添加一个具名迁移函数，参数为 `*sql.Tx`，所有 SQL 和其调用的辅助函数必须使用这一个事务
2. 在 `migrations()` 末尾追加更大的 ID。不要修改已发布的基线 `schema`/`indexes` 或旧迁移函数来承载新功能
3. DDL、数据回填、必要索引属于同一个版本，遇到任意错误直接返回；版本记录由执行器完成
4. 不要在事务中启动嵌套数据库事务、调用使用连接池的写方法、发网络请求或执行外部副作用
5. 为新版本添加旧结构升级、二次执行、失败回滚测试。未来若需要分批大回填，应新增明确的 checkpoint/恢复设计，不可用“忽略错误并继续”的方式模拟断点

## 回归测试

`go test -race ./internal/store ./internal/updater ./internal/api` 覆盖：

- 空库、`testdata/migrations/pre_bucket_users.sql` 与 `pre_notification_channels.sql` 两个冻结历史结构
- 缺列、旧字段重命名、DDL 已完成但数据仅部分回填、部分广播结构转换
- 原有一次性迁移的访问分类/凭据宽限期保持不变
- DDL 后、回填中、索引阶段、版本记录写入失败，全部回滚；纠正问题后重试
- 历史重复数据、未知 SQL 错误、数据库 IO 错误与不认识的未来版本
- 并发迁移的单次执行，以及一致性快照权限、无覆盖原子发布和失败清理

升级快照的保留数、磁盘空间、下载权限和恢复步骤见[灾难恢复指南](disaster-recovery.md)。仅回滚二进制不会回滚数据库；恢复旧快照会丢弃快照时间之后的业务写入，必须在停服并保留当前数据副本之后由管理员操作。
