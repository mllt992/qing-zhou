# 轻舟面板 · 计费与退款业务说明

面向**运营者 / 管理员**，讲清楚「积分 → 商品 → 桶 → 计量 → 退款」这条业务链的每一步是怎么算的：
重复购买（同套餐排队生效）、多套餐并存、按剩余比例退款、下架退款分别怎么处理，以及对应的后台操作。

> 术语速记：**积分** = 站内钱包余额；**商品** = 在售的流量包 / 套餐；**桶（bucket）** = 用户持有的一份独立计量的权益。

---

## 一、两类商品

| 类型 | 名称 | 含什么 | 到期 | 计量归属 |
|---|---|---|---|---|
| `plan` | **套餐** | 流量额度 + 有效期（天）+ 可访问节点分组 | 有 | 每份套餐一个独立「桶」 |
| `traffic` | **流量包** | 仅流量额度 | **无（永久）** | 累加进用户的「通用流量池」 |

- **套餐**是主力商品：既限流量又限时间，还决定能用哪些节点。
- **流量包**是加油包：只加流量、不带时间、不带节点权限，累进一个永不过期的池子。

---

## 二、桶模型（为什么一个用户能同时持有多个套餐）

用户的每一份权益都是一个**独立的桶**，各自拥有：

- 自己的**流量额度 / 已用流量 / 到期时间**；
- 自己的 **sing-box 计量身份**（套餐桶 `qz_<用户>_p<订单号>`，流量池 `qz_<用户>_pool`）；
- 套餐桶还绑定自己**这个商品的节点分组**。

因此：**某个套餐到期或跑满，只下线它名下的节点，不影响用户持有的其它套餐。** 面板对外展示的「总流量 / 总已用 / 最晚到期」是把所有桶聚合出来的汇总值，真正做限额判定的是各个桶本身。

```
用户 A
├── 桶① 套餐「高级 100G/30天」  → 额度100G 已用20G 到期6/30 → 绑「高级」分组节点
├── 桶② 套餐「日本专线 50G/30天」→ 额度50G  已用5G  到期7/10 → 绑「日本」分组节点
└── 桶③ 通用流量池              → 额度30G  已用12G 永久     → 走免费/已授权节点
```

## 三、购买逻辑

所有购买都在**单个数据库事务**内完成：校验余额/库存 → 扣积分 → 写订单（含商品快照）→ 应用权益 → 下发 sing-box。
**任一步失败则整体回滚**，积分不丢、额度不变。库存用 `BEGIN IMMEDIATE` 写锁串行化，杜绝超卖。

### 3.1 首次购买套餐
新建一个套餐桶：额度 = 商品流量，到期 = `现在 + 有效期天数`，并绑定该商品的节点分组。

### 3.2 重复购买**同一个**套餐 → 排队生效（不再叠加）
买第二份同名套餐**不会**把流量/时间叠加到当前这份上，而是**新开一个独立的桶并排队**：

- 当前这份还**能用**（未过期且未跑满）时，新买的份处于**排队中**状态——不计时（`到期=0`）、也不出现在订阅/配置里；
- 等当前这份**跑满流量或到期**，排队的下一份**自动顶上**，此刻才开始算它的有效期（`到期 = 启用时刻 + 有效期天数`）。这个「跑满/到期后顶上」由后台约 1 分钟一次的定时器负责，购买当下若正好没有生效中的同款套餐则**立即启用**。

> 例：持有「100G/30天」剩 10 天，再买一次 → **不是** 200G / 剩 40 天，而是当前份继续用，等它用完（或到期）后第二份 100G/30天 才启用、再给整整 30 天。**一次只跑一份，买再多份按购买顺序排队依次启用**，有效期不会在还没轮到时白白流逝。
>
> 这是与早期版本的关键差异：旧版重复购买是「续费叠加」（合并成一个桶、流量累加、到期顺延）；现在改为**排队**，用完一份接一份。

### 3.3 购买**不同**套餐 → 各自独立
买另一款套餐会**新开一个独立桶**，与已有套餐并存，各自计量、各自到期、各自节点（见第二节示例）。

### 3.4 购买流量包 → 累加进池子
不新开桶，直接把流量**加进用户的通用流量池**（池子不存在则创建）。流量包永不过期。

### 3.5 管理员直接开通（赠送）
后台可不扣积分给用户开通某商品，权益变更与购买**完全一致**，只是记一条 0 积分订单用于审计。

### 3.6 `current_plan_id` 指针
每次买套餐会把用户的「当前套餐」指针指向**最近购买的那款**，用于统计订阅人数等；它只是一个指针，不影响其它桶的独立性。

## 四、计量与判定

- 每次流量统计轮询，把 sing-box 各计量身份的增量记到**对应桶**，并镜像到用户汇总与时序图。
- 一个桶「可用」的条件：**未过期 且 未超额度**（流量池还要求余额为正）。
- 桶跑满或到期 → 它的计量身份从所属入站中移除 → 该套餐名下节点对用户消失，其它桶不受影响。

---

## 五、退款逻辑（按剩余比例）

退款只退**没用掉的那部分**，而不是一律全额。核心一句话：

```
退款积分 = round( 原价 × 可退比例 × (1 − 手续费%) )
可退流量 = min( 本单流量额度 , 该桶当前剩余额度 )          # 剩余 = 额度 − 已用，钳制 ≥ 0
流量剩余比例 = 可退流量 / 本单流量额度
时间剩余比例 = min(本单有效期, 该桶剩余有效期) / 本单有效期
```

### 5.1 计算基准（套餐同时含流量与时间）

套餐有流量、时间两个维度，用哪个算比例由**设置**决定，默认 **`min` 取更小**：

| 基准 | 含义 | 适用 |
|---|---|---|
| **min（默认，推荐）** | 取「流量剩余比例」与「时间剩余比例」中的**更小值** | 防两头薅：既防「用光流量再退」，也防「耗到快过期再退」 |
| traffic | 只看剩余流量 | 你只在意流量成本时 |
| time | 只看剩余时间 | 纯按天计的订阅制 |

> **流量包**无有效期，恒按流量比例，与基准设置无关。

### 5.2 举例

| 场景 | 原价 | 流量 | 时间 | min 比例 | 退款 |
|---|---|---|---|---|---|
| 100G/30天，用了 50G，才第 5 天 | 100 | 剩 50% | 剩 ~83% | **50%** | 50 |
| 100G/30天，用了 99G，第 29 天 | 100 | 剩 1% | 剩 ~3% | **1%** | 1 |
| 100G/30天，几乎没用但挂了 29 天 | 100 | 剩 99% | 剩 ~3% | **3%** | 3 |
| 100G/30天，完全没用、当天退 | 100 | 剩 100% | 剩 ~100% | **100%** | 100 |
| 流量额度已用尽 | 100 | 剩 0% | — | **0%** | 0（权益仍撤销）|

### 5.3 退款做了哪些事（单事务、可回滚）

1. 按上面公式算出**实退积分**，退还并写一条退款流水（备注带比例，如「退款(50%): 高级套餐」）；
2. **撤销权益**：排队模型下每张订单是独立的桶，退款**精确移除这一单对应的那个桶**；若它正是生效中的份，排队的下一份自动顶上（旧的「续费叠加」合并桶则退化为扣回未用额度、到期减一个周期，空了才删）；
3. 订单标记 `refunded`，并记录 `实退积分 / 退款时间 / 退款比例 / 退回流量` 供报表与审计；
4. 重下发 sing-box。

> 权益撤销逻辑与是否按比例**无关**——不管退多少积分，未用掉的额度/时间都会被收回。按比例只影响**退多少积分**。

### 5.4 排队/多份下的退款（按订单精确定位）

退款针对**某一张订单**。排队模型下每次购买都是独立的桶，退款就**精确移除这一单对应的那个桶**，各单各算各的剩余比例、互不牵连：

> 桶① 100G（生效中）+ 桶② 100G（同款续购、排队中），当前只在用桶①。
> 退订单②：直接删掉排队中的桶②，不动正在用的桶①（退它按桶②自己的剩余算，排队中没用过 → 近乎全额）。
> 退订单①：删掉生效中的桶①后，排队的桶②**自动顶上**启用、此刻才开始计时。
> 两次退款不会重复退同一段额度。

> 兼容旧数据：早期「续费叠加」时期合并成一个桶的老账户，找不到独立的单桶时会退化为按比例从合并桶里扣减（扣回未用额度 + 一个周期），不会因删桶一次抹掉多单权益。

### 5.5 下架商品的退款

下架（停售）一款仍有人订阅的商品时，会**对每个订阅者按同一套比例规则退款**并清空其该套餐：

> 服务器要到期、把套餐下架时——用户若已用了大半年，`min(流量,时间)` 会让他只拿回**没用完的小部分**，而不是全额退掉已消费的服务。

### 5.6 边界与幂等

- **已用尽**：比例 0 → 退 0 积分，但权益照常撤销。
- **0 元赠送单**：退 0 积分，权益照常撤销。
- **重复退款**：订单状态 `WHERE status='success'` 守卫，二次退款直接判定「已退款」，不会重复退。
- **用户已删除**：不能退款（历史订单保留，只能删记录）。
- **全额退**：管理员可在退款弹窗切「全额退」，或把设置的退款方式设为 `full`，则忽略用量整单退回。

## 六、后台操作

### 退款一笔订单
「**订单管理**」或「用户管理 → 某用户订单」→ 点**退款** → 弹窗显示**退款预览**（原价 / 已用 / 可退流量 / 流量·时间剩余比例 / **应退积分**）→ 可切换「按剩余比例 / 全额退」→ 确认。
- 已退款订单卡会显示实退积分与百分比；「已退款」统计按**真实退款额**汇总。

### 退款策略（全局默认）
「**系统设置 → 退款策略**」：

| 配置项 | 键 | 默认 | 说明 |
|---|---|---|---|
| 退款方式 | `refund_mode` | `prorated` | 按剩余比例 / 全额 |
| 套餐计算基准 | `refund_basis` | `min` | min / traffic / time |
| 手续费(%) | `refund_fee_percent` | `0` | 从退款中扣除的手续费 |

> 下架退款同样遵循这里的策略。改动即时生效，只影响之后发生的退款。

### 直接开通（赠送）
「用户管理 → 分配套餐」不扣积分给用户开通，记 0 元订单。

### 移除一套餐（不是退款）
「用户管理 → 套餐面板 → 移除」只撤掉那一份权益，**积分不退、订单不动**。额度写在这一份自己的桶上，所以：

- **排队中（尚未生效）的份**：还没开始计量，移除时**全部流量一并收回**；
- **生效中的份**：剩余流量随这份一起失效；若同套餐还有排队的下一份，会立刻顶上。

需要退积分请走「订单 → 退款」。

### 调整流量
「用户管理 → 套餐面板 → 某一份 → 调整」按 GB 给这一份加减额度（正数增加、负数扣减）。扣减不会低于该份已用流量；额度为 0 就是没有可用流量，可以通过增加额度恢复。已过期或已退场（被下一份顶掉）的份加流量不会重新生效，请改调使用中/排队中的份，或再分配一份。这同样不是退款：积分与订单都不动。

## 七、运营建议

- **默认 `min` 基准**最稳，适合绝大多数机场型业务；只有纯按天订阅才建议切 `time`。
- 想覆盖结算/通道成本或抑制反复薅羊毛，可设 3%–10% 手续费；追求口碑则设 0。
- **下架优先于硬删**：直接删商品不会退款、也不清订阅者，走「下架」流程才安全。
- 退款前先看**退款预览**里的应退积分，确认无误再点确认；金额以预览为准。
